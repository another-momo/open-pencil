## 第一部分：基于文档的复盘

### 1. 已被验证做对的设计决策

1. **"工具结果注入 > prompt 规则"的可靠性排序**（`../plans/knowledge/methodology.md` §1）。R2-1 证明 prompt 警告出现 3 次 AI 也不改，而带真实 ID 的 note 一次生效。这是实测换来的最有价值的认知，且已泛化为规则注入优先级（工具返回值 → prompt 硬规则 → prompt 一般指引）。
2. **可判定性划分**："能写成对比当前值和应有值的检查进代码，其余进 prompt"。validate（代码强制）vs 视觉一致性检查（AI 判断）的分层清晰，避免了让模型自证。
3. **错误目录驱动的实测迭代**（`../plans/knowledge/error-catalog.md`）。三轮冒烟产出 17 条带根因的错误记录，修复都落在确定性机制上（`parseJsonArrayParam`、`font_family`、`normalizeSize`），而非堆 prompt——方向正确。
4. **L3 的问题定位准确**："流程形态与工作形态不匹配"（起点/迭代/终点三断点）比"交互摩擦"更深；需求单节点用 pluginData 标记 FRAME 而非新节点类型，守住了 .fig 兼容性底线。

### 2. 结构性风险与疑点

1. **设计状态不可验证是当前最大欠债**。`../plans/l2-context-engineering.md` 已诊断三个核心问题（prompt 47% 硬编码运行时数据、对话历史 60K-150K tokens 无裁剪、设计状态 AI 自我见证不可校验），但顶层 plan 的状态行仍停在"第 4 轮回归待跑"——上下文重构与冒烟回归的先后关系没有写清。第 4 轮回归若在旧上下文架构上跑，结论可能作废。

2. **两份 prompt ~100 行重复是已知技术债但低估了**。R3-2（工具描述与 prompt 规则矛盾导致行为错误）说明"多份事实源"本身就是 bug 温床。每修一次规则要同步三处（两份 prompt + 工具描述），同步漏一次就是一个 R3 类错误。

3. **Checkpoint 双轨风险**。L2 把 checkpoint 做成纯对话，L3 正在把结构化交互实体化为 UI（类型 chips、占位补全清单）。需要警惕双轨期：AI 发文字 checkpoint 和 UI 卡片 checkpoint 哪个是事实源？ask 工具 + 选项卡片在 L3 路线图中定位是"体验优化"，实则为 checkpoint 架构演进的主线，应升格。

4. **注册表键控的地基问题**。当前营销会话状态按 SceneGraph 键控（一份文档一个类型），制作清单要求按根 frame 键控（一份文档多类型并存）。L2 第 4 轮护栏测试若通过，代码是"按旧假设对"——制作清单一启动就要改。建议 L2 打磨收敛后再动键控，避免测试期改地基。

5. **validate 的"询问用户再修复"语义依赖 AI 自觉**。这只是一条 prompt 规则，按注入可靠性排序属于第二级。第 4 轮护栏测试若验证不通过，应考虑 validate 返回结果本身携带"禁止自动修复"的指令文本（复用工具结果注入路径）。

## 第二部分：跳出文档的架构复盘

### 1. 最根本的架构盲区：Agent 是"瞎子"

整个系统建立在 `describe`（结构化数据）之上，AI 从头到尾**看不到画布**。这不是 L3 文档里轻描淡写的"技术短板"，而是架构级缺陷：

- 配色是否和谐、构图是否平衡、文字是否压图、生成图内容是否符合预期——设计的本质问题全部不可见，只能靠启发式 lint（subpixel、fill matches parent）间接推断，而冒烟测试已证明这类 lint 信噪比差（R3-4）。
- 用户拖入的产品图 AI 不知道画的是什么，素材角色完全依赖用户命名——直接架空了"多来源素材协调"（§1.4）和"图片风格协调"（§6.3）两个设计理念。
- **canvas → 截图 → 多模态模型**的视觉回路缺失，系统质量上限被锁死在"盲排版"水平。当前所有 checkpoint 实质上都是让用户充当 AI 的眼睛。

### 2. 质量无度量：迭代靠手感

- 没有 eval 体系：4 轮冒烟测试全是开发者手动跑、肉眼看 log。prompt 每改一条规则，没有任何机制知道是否回归。错误目录方法在 7 个类型 × 多模型下不可扩展。
- 没有成功指标：什么叫"好"？首图可用率？用户改动手数？一轮对话成本？没有定义，Phase 3"实测迭代"就没有收敛判据。
- 错误目录沉淀的知识是**模型特异的**（JSON 尾部垃圾、mt 幻觉），换模型/模型升级后这些补丁可能失效或变成噪音，但没有抽象层隔离。

### 3. 质量下限无保障：骨架全靠模型现场生成

模板体系只覆盖锚点组件（BrandBar/CTABar），**section 骨架每次由模型即兴创作**。设计质量完全取决于模型当时的设计能力和 prompt 遵循度——方差极大，而目标用户（不懂设计的运营）恰恰没有鉴别力，CP4 的"用户把关"是虚的。

- "存为模板"的积累策略存在冷启动问题：库里是空的，早期用户全是小白鼠。
- 更优路径未被考虑：**variant 生成范式**——低成本出 3-5 个结构变体（只变排版，不重新生图）让用户挑，比单线程四阶段 checkpoint 更匹配"运营挑一个顺眼的"的真实心智。当前架构是单线对话，结构上不支持。

### 4. 价值主张与优先级错位

一句话目标是"品牌一致"，但品牌包被排到"长期"、L3 里又降到"优先级最低"。结果：

- 三断点分析自己说"80% 的图是同一品牌的下一张"，但每一次使用品牌信息仍靠 CP1 重新问答——**起点断点实际上没被解决**，只是被需求单绕过（需求单要用户每次手填品牌信息）。
- 制作清单（迭代断点）排在品牌包之前的优先级判断值得重新论证：系列出图的痛点前提是"每张都对"，品牌不一致时 5 张一起错。

### 5. 并发与状态：用户是系统的隐形写入者

"用户在 Checkpoint 之间可以手动操作，但 AI 不感知"——这条被当作特性写进 §8.2，但它埋下全局性问题：

- 设计状态（AI 自述的摘要、注册表、validate 基准）都假设画布只有自己一个写入者。用户手动调整配色后，AI 的状态摘要已失真且无人知晓。
- undo 语义同理：AI 一轮几十次操作全部进用户撤销栈，没有事务边界。用户 Ctrl+Z 会逐帧回放 AI 的工作。
- 协作模式（Yjs 多人）下问题放大，文档完全未触及。

### 6. 逃逸舱失控：eval 工具

R3-3 的修复方式（加 `font_family`）是对的，但它揭示了一个模式：**工具能力缺口 → AI 走 eval（任意 Plugin API 脚本）**。eval 是万能逃逸舱，意味着：

- 工具覆盖不足不会表现为失败，而是表现为脆弱的 eval 脚本（getNodeByIdAsync 用错浪费步骤就是实证）。
- eval 无约束、无校验、不进 validate 视野，也不消耗"修复重试 2 次"这类护栏。
- 应有机制：AI 每次用 eval 都记录为"工具缺口信号"，定期转成正式工具。

### 7. 规格层在代码里：长尾平台怎么办

7 个素材类型硬编码在 `material-types.ts`，但现实是平台规格**长尾且持续变化**（抖音、快手、视频号、淘宝各坑位、审核规范更新）。代码内置意味着：加一个类型要发版；运营无法自助；规格时效性无人维护。"为后续 JSON 配置化留路"只是接口形态预留，没有回答"谁维护、怎么更新、错了谁兜底"。

### 8. 经济性没有核算

单张主视觉 60-70 秒，8 section 长图 = 60-106 次工具调用 + 10 万级 token + 多张生图，端到端可能 15-30 分钟一张图。目标用户的真实节奏是"活动上线前 1 小时出 5 张"。延迟、token 成本、生图成本三者没有任何预算目标，制作清单又是串行——架构上没有并发/流水线的设计位置。

### 9. 跳出视角的优先级建议

| 优先级 | 问题 | 理由 |
|---|---|---|
| P0 | 视觉回路（截图 → 多模态） | 决定产品质量上限，越早接入后续所有规则越有的放矢 |
| P0 | eval 体系 + 成功指标 | 没有它，Phase 3"实测迭代"和第 4 轮回归都没有判据 |
| P1 | 品牌包优先级重排 | 核心价值主张不该排在最后 |
| P1 | 骨架模板种子库 / variant 范式验证 | 质量下限比 checkpoint 数量更影响用户体验 |
| P2 | eval 使用监控 → 工具缺口信号 | 低成本，防逃逸舱失控 |
| P2 | AI 操作事务边界 + 用户编辑感知 | 状态一致性的地基，制作清单启动前必须想清楚 |

## 总结

**文档内视角**：设计的最强项是"实测驱动 + 可判定性分层"的方法论闭环；最大隐患是上下文架构（历史无裁剪、状态不可验证、prompt 双份硬编码）——已被自己的文档诊断清楚，但顶层 plan 的状态行还没跟上这个优先级判断。

**跳出视角**：文档内的迭代（prompt 规则、上下文工程、护栏）都在优化"AI 按规矩干活"，但最大的三个洞是——**AI 看不见画（视觉回路）、没人能量化干得好不好（eval 体系）、每次从零即兴画骨架（质量下限）**。这三个不解决，文档内的打磨是在一个低天花板上精益求精。
